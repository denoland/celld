docs/sqlite-replica‑integration‑plan.txt
========================================

1. Current state
   • ProcessManager eagerly creates a valid (header‑initialised) SQLite file for every room.  
   • SqliteReplica can write its Litestream YAML, restore a DB, start replication, and shut down.  
   • bootstrap.ts lazily opens room.db the first time user code touches it.  
   • No replication is started yet; ProcessEntry has no field for SqliteReplica.  

2. Why Litestream fits
   • One replica process per room DB is enough.  
   • Litestream handles WAL streaming and snapshots.  
   • A graceful SIGTERM flushes the final WAL segment.  
   • A header‑valid but empty DB is safe (Litestream treats it like a new database).  

3. Integration strategy (in words)
   Step A – extend ProcessEntry  
     – Add `replica: Option<SqliteReplica>`.

   Step B – create replica in get_or_spawn_process  
     – Build a SqliteReplica after paths are resolved.  
     – `await replica.restore_if_needed()` (creates file if missing, or downloads snapshot).  
     – Call `replica.start_replication()` 
     – Store `Some(replica)` in the new ProcessEntry.

   Step C – reaper / shutdown  
     – When a room isolate is reaped, if `replica.is_some()`  
       • `replica.wait_for_flush(Duration::from_secs(2)).await`  
       • `replica.shutdown().await`  
     – Then kill the Deno child via the existing `parent_exit_guard`.

   Step D – S3 / MinIO config helper  
     – Implement `get_s3_cfg_for_tenant(tenant) -> Option<S3Config>`  
       (env‑driven for MVP).

   Notes on blocking  
     • restore_if_needed uses `tokio::process::Command` already (non‑blocking).  
     • start_replication uses tokio::process (non-blocking).
     • retain eager empty‑DB creation as a fallback if restore fails.
